## 目标架构

客户端 → HTTPS/WSS入口 → 账号与匹配API / 按match_id路由的游戏连接 → 每桌一个Godot进程。

初期一台 Linux 主机，Caddy、Node.js/TypeScript API、PostgreSQL、独立进程管理器。具体依赖在实现时锁定维护版本并生成锁文件。数据库保存身份、会话、匹配归属与战绩；招募和战斗运行状态保留在各桌内存。暂不引入 Redis 或 Kubernetes。

管理器用受限系统账号运行，只有它能创建游戏子进程；API无任意命令执行能力，不挂载宿主Docker控制套接字。游戏端口仅监听内部地址，公网只提供443及必要的证书验证入口；SSH限制管理来源。进程管理采用参数数组和固定产物路径，不拼接玩家提供的shell命令。

## P0：服务端基础与协议拆分

- 从 main.gd 抽出运行规则、倒计时、BOT和网络权威处理。规则仍使用现有 GDScript，不重写成另一套语言。
- 服务端不初始化3D、音效、卡面、菜单；客户端和服务端RPC节点路径及签名必须一致并实际验证。
- 稳定 seat_id 用于规则；account_id → match_id / seat_id → 当前peer_id单独映射。审查规则、战斗对手、观战和回放中所有ID引用。
- 定义 protocol_version、game_version、content_hash；公共匹配禁用客户端自带MOD覆盖权威规则。版本不符在排队前拒绝，局内仍复核。
- Linux构建记录源码提交、引擎版本、资源清单、SHA-256；服务器健康就绪必须由真实监听和规则加载结果确认。
- 验收：双客户端完成购买、施法、回放、结算及私有信息隔离；单机与原LAN回归通过。

## P1：账号、登录与客户端大厅

- 第一版用户名+密码注册/登录，昵称独立于唯一账号名；不依赖短信或第三方登录。账号标准化、唯一索引和长度限制。
- 使用成熟库实现 Argon2id 密码哈希；按压测调整成本。限制注册/登录尝试，错误提示不泄露账号是否存在。
- 短期访问凭据、可撤销且轮换的刷新凭据；服务端只存刷新凭据哈希；注销、修改密码使相关会话失效。
- Windows/Android凭据持久化接系统安全存储；未实现安全存储前采用会话登录，不把密码或长期token写入普通ConfigFile。
- 首版提供一次性恢复码（服务端只存哈希）与重置密码流程；邮件找回待邮件服务确定后接入。
- 客户端增加登录、注册、恢复、退出、服务器状态、匹配及当前对局入口；离线游戏仍可直接进入。
- 最小数据：accounts、sessions、recovery_codes、matches、match_players、results；分数后置，首版只记权威名次和时间。
- 验收：重名并发注册、错误密码限流、token过期/重放、退出撤销、恢复码重复使用、越权查看数据。

## P2：匹配与最多8桌调度

- FIFO休闲匹配，按协议与玩法分池；先不做段位匹配。建议默认8席，等待60秒后至少2真人可补BOT；均为可配置产品默认值。
- 同账号只能排一个队或占一个活跃席位；重连玩家优先恢复旧局，不能重复排队。
- 默认最多8桌、每桌8席；桌位用原子预留限制。大厅/队列另设连接与长度上限，满载给出等待提示。
- 状态：queued → reserved → connecting → playing → finished / aborted。匹配成功先保留席位，连接超时（建议30秒）按规则释放/补位；取消与分配竞态须有确定结果。
- 入场票据绑定账号、桌、席位、协议、有效期和nonce；一次性消费，票据不能放入会被记录的URL。进程重启后的票据失效必须明确。
- 管理器创建进程、检测就绪、发布路由，失败释放预留并恢复队列；结束回收进程和路由。公共玩家没有房主管理权限。
- API启动恢复数据库中未完成归属，管理器对账存活进程，避免重复开桌、重复排队和遗留端口。
- 验收：64客户端进入8桌，第9桌不超开；取消/掉线竞态；进程启动失败回滚；结算只入库一次。

## P3：原位断线重连（上线前必需）

- 重连凭据绑定稳定账号与席位；连接peer变化不改变英雄、阵容、金币、手牌、排名或对手引用。
- 断网显示重连界面，指数退避加抖动；鉴权成功获取新入场票据，不复用一次性旧票据。
- 建议重连保留120秒，局内计时继续。允许短暂宽限后BOT托管；回来接管服务器当前状态，BOT已执行的合法操作不撤销。不可同时由BOT和真人操作。
- 接管递增连接代次并撤销旧连接操作权；服务端按席位校验代次、action_id及状态版本，防止重发导致重复消费。
- 重连发自己的最新快照、服务端倒计时、阶段与必要回放；战斗中重连可从当前权威结果恢复展示，不重新计算随机结果。
- 全员断线不立即清桌；等待保留期限后再清理。玩家主动投降与短暂断线分开处理；淘汰玩家按观战权限恢复。
- 第一版保证“游戏进程存活时重连”，不承诺主机重启或游戏进程崩溃后续局。崩溃标记aborted，不扣段位、不伪造正常战绩。磁盘检查点恢复作为后续阶段。
- 验收覆盖招募购买前后、发现/抉择、饰品、战斗回放、结算、安卓切后台/Wi-Fi切移动网络、重复登录、全员短断和超时。

## P4：一键部署、运维与发布

- 计划提供 doctor / install / update / status / logs / backup / restore / rollback 子命令；目前不存在可运行部署脚本。
- 配置域名、服务端产物、数据库、最大桌数、匹配时间、重连期限；密码和内部密钥在主机生成或通过受保护文件注入，不写Git与日志。
- 数据库迁移、可重复安装、受限用户、服务自动启动、日志轮转、HTTPS和WSS检查。
- 更新先停止新分配、等待当前对局结束，再换服务端；既有客户端按兼容版本分池。维护超时须显式提示，不强杀正常对局冒充无损更新。
- 保留前一版产物与数据库备份；数据库不兼容迁移不能只回滚镜像，必须有明确恢复步骤及演练。
- 监测在线/排队/每桌人数、进程RSS、CPU峰值、每场战斗耗时、出站字节、错误率、重连成功率和数据库磁盘。
- 提供关闭注册/暂停匹配/维护公告/账号封禁与审计的管理命令；管理端不暴露普通玩家权限。

## P5：上线门槛

1. 64个真实协议客户端，8桌同时运行并连续至少2小时；测量空闲/招募/复杂连锁/集中结算，不能用仅运行BOT规则的模拟替代网络负载。
2. 记录P95/P99操作响应、事件循环延迟、战斗结算耗时、RSS和公网出站峰值。初步预算为CPU持续低于70%、内存低于75%、带宽持续低于70%；它们是待验证预算，不是现有测试结论。
3. 重连、重复请求、跨账号票据、伪造结果、越权房主管理、畸形大包与限流测试通过；监测内存无持续增长。
4. 备份恢复、API重启、游戏进程故障、维护排空和回滚演练，确认用户看到明确状态。
5. 最终Windows与Android客户端完成两个外部网络真实联机；同机/模拟器结果单列，不替代实机验证。

建议按P0→P1→P2→P3→P4→P5交付；P4的部署骨架可在P0完成后提前建立。服务器到位只能解锁Linux、公网和容量实测，不能跳过其余实现。完整恢复、段位/MMR、好友组队、邮件找回、多主机扩容后置。
